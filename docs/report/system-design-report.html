1 · Summary

Juthoor at a glance

Juthoor, Arabic for “roots”, is a bilingual genealogy platform that helps Palestinians worldwide rebuild, connect and preserve their family trees. It is Arabic first and right to left, follows the GEDCOM 7 genealogy standard, and links separate family trees into one shared Palestine Tree through a probabilistic matching engine.

33pages in the web app
36database tables
48database migrations
110row-level security policy definitions
57SQL functions, including the matching engine
456Palestinian villages and places seeded
116unit test cases, plus 6 end-to-end specs
17database test files

State of the build

  • Core family trees are built. Users can create trees by hand or import GEDCOM files, edit people and relationships on a visual chart, and export the tree again.
  • Search is built. Family Finder searches across trees with Arabic normalisation, phonetic matching and Latin to Arabic transliteration.
  • The matching engine is built and set to review only. Automatic merging is off by default. Matches go to an admin queue or to both tree owners.
  • Privacy for living people is partly built. Search, the people list and the relationship path hide living people’s details. The GEDCOM export does not yet.
  • Contact, moderation and access logging are not built yet. They are listed in section 10 together with the decisions they depend on.

4 · System architecture

Three tiers and a delivery pipeline

The browser talks to a Next.js server on a private server. The Next.js server talks to Supabase, which holds the database, sign-in, file storage and live updates. Most business rules live inside the database, so they apply no matter which client calls it.

How a request flows

  1. The browser calls the server. Caddy terminates TLS and passes the request to Next.js.
  2. The proxy checks the session. It refreshes the Supabase session cookie and sends signed-out visitors away from private pages.
  3. Server code calls Supabase as the user. Data loaders and server actions use the user’s token, so every query passes through row-level security.
  4. The database enforces the rules. Policies decide which rows the user may see. Security-definer functions handle sensitive steps such as search masking, access approvals and match decisions.
  5. The page renders on the server. Interactive parts such as the tree chart hydrate in the browser and subscribe to live changes.

Trust boundaries

  • The web app holds no service key. No code in the web app uses the Supabase service role, so a server bug cannot bypass row-level security.
  • Administrators are a database flag. Admin pages check the flag on the server, and the database refuses any attempt to set it through the API.
  • Files are private. Attachments, proof of family and identity documents sit in three private buckets with their own access policies.

7 · Backend and database, continued

Security, search and storage

Security model

MechanismWhat it does
Row-level securityEvery application table has policies. Tree data is readable when the tree is public, owned by the user, or the user is an approved member. Writes need owner or collaborator rights.
Access helperscan_access_tree, can_write_tree, is_tree_owner, is_tree_member and is_admin are shared by the policies.
Definer functionsSearch, access approvals, match decisions and link changes run as security-definer functions with a pinned search path. Each one checks the caller itself.
Living-person maskingis_person_living treats anyone without a death record and born less than a century ago, or with no birth year, as living. Search hides their birth year and village from non-members; relationship paths show “Hidden relative”.
Match privacyOwners never read the raw match table. They see a masked card view. Pairs with a living person are never merged by an admin; both owners must accept.
Admin guardA trigger blocks any change to the admin flag made through the public API.
Storage policiesFiles live under a folder named after the uploader. Policies allow the uploader, the tree owner or administrators, depending on the bucket.

Family Finder search

Search runs in one database function. It normalises Arabic spelling, builds phonetic keys and compares names with trigram similarity. It scores given name, family name, father, mother, birthplace and birth year, and returns a score breakdown. Private trees are redacted, and living people lose their birth year and village unless the searcher is the owner or an approved member.

7 · Backend and database, continued

The matching engine

The matching engine finds the same person recorded in different family trees. It is written in SQL and follows the Fellegi-Sunter method used in record linkage.

StageWhat happens
1. Change queueTriggers on people, names, events and families put the person and close relatives into a queue whenever data changes.
2. FeaturesEach queued person gets a feature vector: transliterated, normalised and phonetic names for self, parents, grandparents and spouses, plus life facts.
3. BlockingSeveral blocking passes pick candidate pairs from different trees. Caps stop oversized groups from slowing the run.
4. Scoringscore_pair weighs 25 fields. Hard vetoes reject pairs with a different gender, the same tree, birth years more than 15 years apart, or a privacy hold.
5. RoutingPairs with a living person become masked hints for both owners. Other pairs go to the admin review queue. Automatic merging is switched off by default.
6. LinkingA confirmed link joins two records. Links form the Palestine Tree overlay. Any link can be revoked, which removes its notifications, relay tokens and cached paths.
Open point. The batch function exists, but no schedule is defined in the repository. Running it nightly needs a scheduled job in Supabase or on the server.

Environments and migrations

  • Local. The Supabase CLI runs the full stack in Docker. A reset builds all 48 migrations from scratch, and a demo seed creates trees, people, matches and verifications.
  • Production. Hosted Supabase on PostgreSQL 17. Migrations are applied by hand after testing locally. The security fixes of 12 October 2026 are now recorded in the migrations folder.
  • Types. The TypeScript database types are maintained by hand. Running the type generator overwrites them, so each new table is added manually.

Decisions needed from the steering group

  1. Shared people. Who approves when one person sits in several family trees.
  2. Villages and places. Who builds and maintains the list, and which sources count.

Glossary

PFTPalestine Family Tree. The combined tree formed by linking all individual trees.
IFTIndividual Family Tree. One user’s own tree.
VCCVillage, city or camp. A place of origin.
GEDCOMThe standard file format for exchanging genealogy data. Juthoor uses version 7.
Row-level securityDatabase rules that decide, row by row, what each user may read or change.
RPCA database function called through the API.
Fellegi-SunterA statistical method for deciding whether two records describe the same person.
BlockingGrouping records by shared keys so only likely pairs are compared.
pgTAPA testing framework that runs tests inside PostgreSQL.
